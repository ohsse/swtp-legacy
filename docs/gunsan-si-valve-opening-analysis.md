## 1. 결론 요약

관망해석 시뮬레이션 화면에서 "펌프 적용 및 실행"을 누르면 아래 문구가 뜬다.

> 오류가 발생했습니다: 국가산단밸브: 0~100% 범위의 개도율이 필요합니다 (891-365-POI-8601).

기억해야 할 네 가지:

1. **밸브 설정 문제가 아니다.** 이 메시지의 실질은 **"기준시각 시점의 SCADA 실측이 없다"**이다.
   개도율은 화면에서 입력하는 값이 아니라 `TB_RAWDATA` 에서 읽어 오는 **실측 태그**다
   (`epanet_si_gs.py:87`, `:895`). INP 의 밸브 설정을 아무리 고쳐도 사라지지 않는다.

2. **기준시각과 실측이 서로 다른 테이블에서 온다.** 기준시각은 "방금 배수지 유량을 저장한
   현재 시각"(`TB_EPA_SIM_RESV_FLOW.MAX(UPDT_TIME)`, `epa_service_gunsan.py:188-206`)인데,
   개도율은 그 시각 기준 **과거 600초 창**의 `TB_RAWDATA` 를 본다(`epanet_si_gs.py:463-479`).
   덤프 DB 처럼 실측이 과거에서 멈춘 환경에서는 이 창이 반드시 빈다.

3. **하필 "밸브" 에러로 터지는 데는 이유가 있다.** SI 의 사전 검증은 SI 수요와 **선택 펌프의
   Hz만** 본다(`:589-610`). 그 Hz 는 화면이 직접 보내 실측을 대체하므로 통과한다. 나머지
   실측 태그는 경고만 남긴다. 결과적으로 **`TB_RAWDATA` 를 "없으면 죽는" 방식으로 요구하는
   유일한 지점이 밸브 개도율**이라, 실측 부재가 여기서 처음 표면화된다(§3.3).

4. **"국가산단"이라는 이름은 우연이다.** INP 의 `[VALVES]` 순서상 국가산단밸브가 먼저일 뿐이다
   (`epa/inp/epa_model.inp:494-495`). 지방산단 태그(`891-365-POI-8600`)도 같은 날 멈춰 있어
   (§4.4), 국가산단을 해결해도 바로 다음 밸브에서 막힌다.

**dev DB 실측으로 확정됐다**(§4.4). `891-365-POI-8601` 의 마지막 값은 `2026-08-24 15:49:00`,
기준시각은 `2026-09-21 11:03:42` — 간격 **약 2,402,082초**로 600초 창의 4,000배다.
그리고 이는 밸브 태그만의 일이 아니다: **군산 `891-365-*` 계열 전체가 `2026-08-24` 에 끊겼다.**
즉 실제 문제는 **이 DB 로의 SCADA 수집이 4주 전에 멈춘 것**이고, 밸브 개도율은 그 사실이
처음 드러나는 지점일 뿐이다(§3.3, §4.2).

**더미 주입으로 반증까지 마쳤다**(§4.6). 네 개 태그에 `2026-08-24` 마지막 실측값을 그대로
채워 넣자 이 오류는 사라지고 국가산단밸브가 정상 계산됐다(개도율 39.73% → 등가 저항 R=10.41).
다만 **바로 다음 관문인 지방산단밸브에서 다시 막힌다** — 8/24 실측이 `95.36875%` 인데 엔진은
98% 이상만 받기 때문이다(§7-7). 즉 이 화면을 끝까지 돌리려면 수집 복구만으로는 부족하고,
**지방산단밸브의 부분 개방을 모델이 표현할 수 있어야 한다.**

남은 미확정은 **수집이 멈춘 이유**와 **현장 DB 의 상태**다(§4.5).

## 3. "SI 개도율"이란 무엇인가

이 설계를 모르면 "화면에서 개도율을 입력한 적이 없는데 왜 개도율 탓을 하나" 싶어진다.

### 3.1 입력값 네 가지의 출처가 서로 다르다

| 항목 | 출처 | 근거 |
|---|---|---|
| 기준시각 `--ts` | `TB_EPA_SIM_RESV_FLOW.MAX(UPDT_TIME)` = **방금 저장한 현재 시각** | `epa_service_gunsan.py:188-206, 245, 253` |
| 배수지 수요량 | `TB_EPA_SIM_RESV_FLOW` (화면에서 저장) | `epanet_si_gs.py:510-525` |
| 펌프 Hz | **화면 입력** `--pump-hz`. 주면 실측보다 우선 | `epa_routes.py:45-72`, `epa_service_gunsan.py:258-260` |
| **밸브 개도율** | **`TB_RAWDATA`** 의 `891-365-POI-8601` / `891-365-POI-8600` | `epanet_si_gs.py:87, 90`, `:452-460`, `:463-495` |

**개도율만 화면에서 줄 방법이 없다.** `VALVE_META` 는 스크립트 상수이고, 웹 요청 페이로드에
개도율을 넣는 경로가 없다.

### 3.2 조회 창은 "기준시각 이전 600초"

```python
WHERE TS >= %s AND TS <= %s AND TAGNAME IN (…)   # epanet_si_gs.py:475
GROUP BY TAGNAME                                  # 태그별 MAX(TS) 1건
```
인자는 `(target - timedelta(seconds=fallback_sec), target)`(`:480`).
`fallback_sec` 은 `GUNSAN_FALLBACK_SEC = 600`(`epa/config.gunsan.py:84`)에서 오며
`_common_argv()` 가 `--fallback-sec` 로 넘긴다(`epa_service_gunsan.py:143`).

**미래 방향은 보지 않는다.** 기준시각보다 뒤에 있는 실측은 쓰이지 않는다. (고산 엔진은 전·후
양쪽을 보는데 군산은 과거만 본다 — 선행 문서 §8-8.)

창이 비면 태그가 `readings` 딕셔너리에 아예 없고, `val()` 이 `None` 을 돌려준다.

```python
def val(tag):                                                   # :886-887
    return readings[tag].value if tag and tag in readings else None
...
opening = val(meta.get("opening"))                              # :895
```

### 3.3 세 엔진의 사전 검증 수준이 다르다

| 엔진 | 사전 검증 | 실측이 없을 때의 문구 |
|---|---|---|
| **SI** (`epanet_si_gs.py`) | `validate_si_inputs()` `:589-610` — **SI 수요 + 선택 펌프 Hz만** | 밸브 단계까지 가서 이 문서의 오류 |
| MO (`epanet_mo_gs.py`) | 없음 | 같음 (`:766`) |
| PRE (`main_epa_gs.py`) | `validate_runtime_inputs()` `:837-875` (호출 `:1707`) | **"PRE 해석에 필요한 실측 운전조건이 없습니다: 891-365-POI-8601 (국가산단밸브: 개도율), …"** |

PRE 만 **없는 태그를 목록으로** 알려 준다. SI 는 그 검증이 없어서, 실측이 통째로 비어 있어도
경고 한 줄만 남기고 지나간다.

```python
missing_optional = sorted(set(si_raw_tags()) - set(readings))   # :1362
if missing_optional:
    print("[WARN] 미조회 실측 태그(비교용 포함): " + ", ".join(missing_optional))
```

**이 `[WARN]` 줄이 §5 의 진단 열쇠다.**

## 4. 원인

### 4.1 판정 두 줄

`epa/epanet_gunsan/epanet_si_gs.py:921-922`

```python
if opening is None or not 0 <= opening <= 100:
    raise ValueError(f"{vid}: 0~100% 범위의 개도율이 필요합니다 ({meta['opening']}).")
```

이 조건이 참이 되는 경우는 셋뿐이다.

| # | 조건 | 판정 근거 | 이번 건 |
|---|---|---|:--:|
| a | 기준시각 이전 600초 창에 `891-365-POI-8601` 행이 **없다** → `opening is None` | `:463-480` 가 아예 행을 못 가져옴 | **확정**(§4.4) |
| b | 행은 있으나 `VALUE` 가 NULL·비숫자·NaN·Inf → 걸러져서 `opening is None` | `:489-494` 의 `float()` 예외 / `math.isfinite()` 탈락 | 배제 |
| c | 값은 있으나 0~100 밖 (스케일 이상, 음수 등) | 값이 살아서 범위 검사에 걸림 | 배제 |

(a)(b) 는 `opening is None` 으로 같은 지점에 도달하지만 조치가 다르다. §5-① 로 (a)(b) 와 (c) 를
먼저 가르고, §5-②③ 으로 (a) 와 (b) 를 가른다. **이번 건은 §4.4 의 실측으로 (a) 가 확정됐다**
— 값이 걸러진 것이 아니라 행 자체가 4주째 들어오지 않는다. §5 는 같은 증상이 다른 환경
(특히 현장)에서 재발했을 때 다시 밟기 위한 절차로 남겨 둔다.

### 4.2 왜 다른 검증은 안 걸리고 여기까지 오는가

`validate_si_inputs()`(`:589-610`)가 실패시키는 조건은 셋이다.

```python
if not si_demands:              # :591  TB_EPA_SIM_RESV_FLOW — ①이 방금 저장했으므로 통과
missing_demands = …             # :595  같은 테이블 — 통과
missing_hz = …                  # :601-605  ← 여기가 핵심
    if num not in hz_overrides and hz_tag not in readings:
```

**`hz_overrides` 에 있으면 `TB_RAWDATA` 를 보지 않는다.** 화면이 펌프마다 Hz 를 반드시 채워
보내고(`epa_routes.py:56-58` 이 빈 Hz 를 400 으로 막는다), `_fmt_pump_hz()` 가 `--pump-hz` 로
넘긴다(`epa_service_gunsan.py:258-260`). 따라서 **선택한 펌프는 전부 `hz_overrides` 에 있어
이 검사를 통과한다.**

남은 실측 태그(비교용 압력·유량)는 `[WARN]` 으로만 처리된다(`:1362-1367`).
**그래서 밸브 개도율이 `TB_RAWDATA` 부재를 처음으로 드러내는 관문이 된다.**

> 뒤집어 말하면, 화면에서 Hz 를 비워 두고 실측 Hz 에 맡기는 경로였다면
> "선택 펌프의 Hz가 없습니다"(`:607-609`)라는 **훨씬 정확한 문구**가 먼저 떴을 것이다.

### 4.3 왜 "국가산단"인가 — 밸브 순서일 뿐이다

`configure_valves()` 는 `for lid, old in list(wn.valves())`(`:892`)로 **INP 정의 순서대로** 돈다.

`epa/inp/epa_model.inp:488-495` (dev 컨테이너가 실제로 읽는 `./.data/files/epa_model.inp` 도 동일)

```
[VALVES]
 B52    Bkj-1609  B37       1800  FCV  40000  0     ← VALVE_META 에 없음 → 강제 OPEN (:916-919)
 B49    Bks-1216  B33        600  FCV  72000  0     ← 〃
 4      Bks-2304  2          500  FCV  12000  0     ← 〃
 23     14        Bjj-2060   900  PRV      0  0     ← 〃
 국가산단밸브  16   Bks-2361   150  FCV  35000  0     ← :494  **첫 번째 meta 보유 밸브**
 지방산단밸브  13   17         600  FCV  35000  0     ← :495
```

앞 4개는 `VALVE_META` 에 없어 `mode == "open" or not meta` 분기(`:916-919`)로 조용히 OPEN
처리되고 지나간다. 다섯 번째인 국가산단밸브가 개도율을 요구하는 첫 밸브다.

**따라서 "국가산단"은 고장 지점이 아니라 단지 먼저 검사받은 밸브다.** 지방산단
(`891-365-POI-8600`)도 같이 없을 가능성이 높지만, 첫 밸브에서 예외가 올라가 확인되지 않는다.

| `891-365-PMB-4017` | 펌프 1호기 가동 | `2026-08-24 15:37:00` | 1,910,371 |

여기서 읽어야 할 것 다섯 가지:

1. **원인 (a) 확정.** 기준시각 `2026-09-21 11:03:42` 기준 600초 창은
   `10:53:42 ~ 11:03:42` 인데, 이 태그의 마지막 값은 `2026-08-24 15:49:00` 이다.
   간격 **27일 19시간 14분 42초 ≈ 2,402,082초** — 창의 약 4,000배다.

2. **밸브 고유의 문제가 아니다.** 군산 `891-365-*` 계열이 개도율·압력·유량·펌프까지
   **전부 `2026-08-24 15:37~15:56` 에 끊겼다.** 계측기 몇 개가 아니라
   **이 DB 로의 수집 자체가 그날 중단**됐다. 함열(`740-914-*`)만 이틀 더 가서 `08-26 15:32` 다.

3. **선행 문서의 원인은 해소됐다.** `SI base` 가 `2026-09-21 11:03:42` 로 찍혀 있다
   — "①저장"이 정상 동작했고 `_latest_si_ts()` 가 값을 돌려주고 있다는 직접 증거다.
   `DB NOW(11:37:21) > SI base(11:03:42)` 이므로 그 문서가 지목한 시계 스큐도 지금은 없다.

4. **§4.3 의 추정이 확인됐다.** 지방산단 태그(`891-365-POI-8600`)도 `08-24 15:56` 에서 멈췄다.
   국가산단을 해결해도 **바로 다음 밸브에서 같은 벽**을 만난다.

5. **펌프 Hz 태그도 죽어 있는데 검사를 통과했다**(`891-365-SPI-4000`, `08-24 15:40`).
   §4.2 의 "화면이 보낸 `--pump-hz` 가 실측을 대체한다"가 실측으로 확인된 셈이다.
   화면이 Hz 를 보내지 않았다면 더 정확한 문구가 먼저 떴을 것이다.

> **이 문서를 처음 쓸 때는** 같은 DB 의 `TB_FP_SI_VAL` 최신값(`2025-05-08`, 선행 문서 §4.3)과
> 보정파일 스냅샷(`gunsan_valve_model.json:242-250`)을 근거로 "실측이 1년 이상 과거에서
> 멈췄다"고 **추론**했으나, 실측 결과 `TB_RAWDATA` 는 `2026-08` 까지 들어와 있었다.
> 그 두 테이블은 시간축이 서로 다르다 — 추론의 근거로 쓸 수 없다.

### 4.5 미확정

- **수집이 `2026-08-24` 에 멈춘 이유**는 이 조사 범위 밖이다. dev DB 로의 동기화가 끊긴
  것인지, 원천 SCADA 쪽이 멈춘 것인지 확인되지 않았다.
- **현장(`deploy/gunsan/`)의 `TB_RAWDATA` 상태**는 관측하지 않았다. 이 문서의 실측은
  전부 dev DB(`<internal-host>`) 기준이다.
- 원인 (b)(c) 는 배제됐다 — 값이 걸러진 것이 아니라 **행 자체가 없다.**

### 4.6 실증 — 더미 주입 후 엔진 직접 실행 (`2026-09-21 13:26`)

Tier 1+2 네 개 태그에 더미를 넣고(§6.1) 엔진을 CLI 로 돌렸다. 웹 버튼과 같은 인자 구성에
`--ts` 만 기준시각으로 고정했다.

**이 문서의 오류는 사라졌고, 그다음 관문에서 멈췄다.**

확인된 것 네 가지:

1. **원인 (a) 가 맞다.** 행만 채우니 `0~100% 범위의 개도율이 필요합니다` 가 사라졌다.
   값을 고친 것이 아니라 **없던 행을 넣었을 뿐**이다.

2. **국가산단은 설계대로 동작한다.** 실측 개도율 `39.73125%` → 35점 보정곡선 보간 →
   등가 저항 `R = 10.4108` → TCV `ACTIVE` 로 치환(`:936-961`).

3. **§4.2 가 실측으로 확정됐다.** 펌프 Hz 태그(`891-365-SPI-4000~4003`)는 여전히 미조회
   목록에 있는데도 `source=argument` 로 통과했다 — 화면이 보낸 `--pump-hz` 가 실측을 대체한다.
   **수집이 4주째 멈춘 사실을 펌프 쪽에서는 아무도 알려주지 않는다.**

4. **§7-7 이 실측으로 확인됐다.** 8/24 지방산단 실측은 `95.36875%` 인데 엔진은 98% 이상만
   받는다. **현장이 실제로 운전하던 상태를 모델이 표현할 수 없다.** 국가산단은 보정곡선이
   있어 임의 개도율을 저항으로 바꾸지만, 지방산단은 곡선도 후단 압력계도 없어
   `98↑=전개방 근사 / 0=폐쇄 / 그 사이=거부` 3단 논리뿐이다(`:929-934`).

> 이 실행은 `--no-save-db` 로 돌렸고, 밸브 단계에서 죽어 DB 쓰기는 없었다.
> 지방산단 개도율을 98 이상으로 올리면 EPANET 수리계산까지 진행되지만, 그것은
> "실측과 다른 밸브 상태로 해석한다"는 뜻이므로 이 문서에서는 하지 않았다.

### 5.1 ① 로그 한 줄 — (a)(b) 와 (c) 를 즉시 가른다

```sql
-- 기준시각: 엔진에 --ts 로 넘어가는 값
SELECT MAX(UPDT_TIME) AS si_base FROM TB_EPA_SIM_RESV_FLOW;

SELECT COUNT(*) FROM TB_RAWDATA
 WHERE TAGNAME = '891-365-POI-8601'
   AND TS BETWEEN (SELECT MAX(UPDT_TIME) FROM TB_EPA_SIM_RESV_FLOW) - INTERVAL 600 SECOND
               AND (SELECT MAX(UPDT_TIME) FROM TB_EPA_SIM_RESV_FLOW);
```

`si_base - raw_latest` 가 600초(`GUNSAN_FALLBACK_SEC`)를 넘으면 (a) 확정이다.

## 6. 해소 방법

근본 해소는 **`TB_RAWDATA` 수집을 되살리는 것**이다. 밸브 태그만의 문제가 아니라 군산
`891-365-*` 계열 전체가 `2026-08-24` 에 끊겼으므로(§4.4), 이것을 고치지 않으면 밸브를
우회해도 **압력·유량 비교값이 전부 빈 채로 해석이 돈다.** 다만 수집이 멈춘 이유는
이 조사 범위 밖이다(§4.5).

아래는 수집 복구 전에 **화면 동작만이라도 확인**하려는 경우의 우회로다.
**어느 것도 코드 변경이 아니다.**

| 방법 | 내용 | 주의 |
|---|---|---|
| **A. 실측이 있는 과거 시각으로 돌린다** | CLI 는 `--ts` 를 받는다 (`epanet_si_gs.py:9`). 실측이 살아 있는 마지막 구간은 `2026-08-24 15:49` 이전이다(§4.4) | **화면 버튼 경로는 그대로 실패한다.** 프런트가 `ts` 를 보내지 않아 항상 `_latest_si_ts()` 를 쓴다 (`epa_routes.py:101`). 또 `TB_EPA_SIM_RESV_FLOW` 는 이력이 없어(선행 문서 §5.2) 그 시각의 배수지 수요량을 되살릴 수 없다 |
| **B. `GUNSAN_VALVE_MODE` 를 바꾼다** | `epa/config.gunsan.py:76` 을 `inp` 또는 `open` 으로. 개도율 요구 자체가 사라진다 (`epanet_si_gs.py:914-919`) | **해석 결과의 의미가 달라진다.** `open` 은 전개방 비교 시나리오, `inp` 는 INP 밸브 설정 유지다. 화면 동작 확인용 한정이며 현장 설정으로 올리면 안 된다. 밸브를 넘겨도 위에 적은 비교값 부재는 그대로 남는다 |
| **C. `GUNSAN_FALLBACK_SEC` 를 늘린다** | `epa/config.gunsan.py:84` | **불가.** 27일 19시간(약 2,402,082초)을 덮으려면 창을 4,000배로 키워야 하는데, 그것은 "4주 전 밸브 상태로 지금을 해석한다"는 뜻이라 해석이 무의미해진다(§4.4) |
| **D. dev DB 의 `TB_RAWDATA` 를 현재 시각축으로 이관한다** | 실측 시간축을 통째로 옮긴다 | **별도 합의 필요.** 태그당 약 191만 행이다(§4.4). 선행 문서 §7.2 의 `FLOW_RATE = 1000`(컬럼 DEFAULT) 문제와 같이 봐야 의미 있는 해석이 된다 |
| **E. 필요한 태그만 더미로 메운다** | D 의 최소 버전. 엔진이 반드시 요구하는 태그(개도율 2개)와 화면 요약용 2개만 최근 구간에 채운다 | **`2026-09-21` 에 이 방법을 적용했다 — 절차는 §6.1, 결과는 §4.6.** 비교값 24개는 여전히 비어 실측 대비 오차는 볼 수 없다 |

**현장(`deploy/gunsan/`)에서 같은 오류가 난다면 진단을 처음부터 다시 밟아야 한다.**
이 문서의 실측은 전부 dev DB(`<internal-host>`) 기준이며 현장은 관측하지 않았다(§4.5).
§5-① 부터 시작하면 된다.

### 6.1 dev 더미데이터 주입 절차 (`2026-09-21` 적용됨)

**dev DB 전용이다. 현장에서는 절대 쓰지 않는다.** 화면 동작을 확인하려고 §4.4 의 빈 구간 중
**필요한 최소 태그만** 메운 것이다. 값은 전부 `2026-08-24` 마지막 실측값을 그대로 복사했고
(지어낸 수치가 아니다), `SERVER='DUMMY_DEV'` 로 표시해 한 줄로 되돌릴 수 있게 했다.

| 태그 | 값 | 근거·제약 |
|---|---|---|
| `891-365-POI-8601` | `39.73125` | 보정곡선 유효범위 `11.06875~51.43125` 안이라 그대로 쓸 수 있다 |
| `891-365-POI-8600` | `95.36875` | **엔진이 거부하는 값이다**(98 미만). 한계를 재현하려고 실측 그대로 두었다(§4.6-4) |
| `891-365-FRI-8950` | `2780` | `TB_TOT_ALG.FLW_VAL` (PIPE 45 실측 유량) |
| `891-365-PRI-4000` | `2.28375` | `TB_TOT_ALG.FP_VAL` (NODE Bks-2496 실측 압력) |

행 형식은 `TS / TAGNAME / VALUE(varchar) / QUALITY='100' / SERVER='DUMMY_DEV'` 이며,
파티션 `p202609`·`p202610` 이 실재해 `2026-09` 삽입이 가능함을 확인했다.

**주입·연장** — 최근 3시간을 분단위로 채운다. PK 가 `(TS,TAGNAME)` 이라 재실행해도 안전하다.

```python
# python - <<'PY'  (리포지토리 루트에서)
import json, pymysql
from datetime import timedelta
VALUES = {'891-365-POI-8601':'39.73125', '891-365-POI-8600':'95.36875',
          '891-365-FRI-8950':'2780',     '891-365-PRI-4000':'2.28375'}
cfg = json.load(open('epa/connections.gunsan.json'))['maria-ems-db-gu-test']
c = pymysql.connect(host=cfg['host'], port=cfg['port'], user=cfg['user'],
                    password=cfg['password'], db=cfg['db'], autocommit=False,
                    cursorclass=pymysql.cursors.DictCursor)
with c.cursor() as cur:                      # 시각은 DB 시계 기준으로 잡는다
    cur.execute("SELECT NOW() AS n")
    now = cur.fetchone()['n'].replace(second=0, microsecond=0)
rows = [(now - timedelta(minutes=k), t, v, '100', 'DUMMY_DEV')
        for t, v in VALUES.items() for k in range(181)]
c.begin()
with c.cursor() as cur:
    cur.executemany("INSERT INTO TB_RAWDATA (TS,TAGNAME,VALUE,QUALITY,SERVER) "
                    "VALUES (%s,%s,%s,%s,%s) ON DUPLICATE KEY UPDATE "
                    "VALUE=VALUES(VALUE), SERVER=VALUES(SERVER)", rows)
c.commit(); c.close()
# PY
```

**삭제**
```sql
DELETE FROM TB_RAWDATA WHERE SERVER = 'DUMMY_DEV';
```

> 확인 쿼리는 반드시 `TAGNAME` + `TS` 로 건다. `WHERE SERVER='DUMMY_DEV'` 는 인덱스가 없어
> 파티션 전체를 훑느라 수 분씩 걸린다.

#### 유효기간과 함정

**더미는 영구적이지 않다.** 기준시각은 버튼을 누른 순간(`TB_EPA_SIM_RESV_FLOW.UPDT_TIME`)이고
창은 그 이전 600초뿐이므로, **더미의 `MAX(TS)` 를 10분 넘겨 지나가면 같은 오류가 다시 난다.**
위 명령을 다시 돌려 "지금"까지 연장하면 된다.

**CLI 로 과거 `--ts` 를 줄 때는 커플링에 주의한다.** 배수지 수요도 같은 창
(`UPDT_TIME BETWEEN target-600s AND target`, `:510-525`)에서 조회하므로,
`--ts` 는 **더미 구간과 `UPDT_TIME` 이 동시에 들어오는 시각**이어야 한다. 한쪽만 맞추면
`TB_EPA_SIM_RESV_FLOW에서 기준시각/fallback 범위의 SI 수요량을 찾지 못했습니다`(`:591-592`)로
바뀔 뿐이다. 화면 버튼은 저장이 `UPDT_TIME` 을 "지금"으로 갱신하므로 이 문제가 없다.

### 6.2 손대지 않은 것

§1~§7 의 진단 단계에서는 코드를 바꾸지 않았고, 관찰된 문제는 §7 에 기록만 남겼다.
더미 값을 98 이상으로 조작해 해석을 통과시키는 것도 하지 않았다 — 실측과 다른 밸브 상태를
가정하는 일이기 때문이다(§4.6).

**대신 §7-7 을 코드 쪽에서 해소했다. §8 을 볼 것.**

## 8. 후속 조치 — 지방산단 임계값 `98` → `95` (`2026-09-21` 적용)

§7-7 을 코드 쪽에서 해소했다. **이 문서에서 유일하게 적용한 코드 변경이다.**

### 8.1 바꾼 것

**세 엔진 모두 적용했다.** 리포지토리에 `98` 임계값 흔적은 남아 있지 않다.

| 파일 | 위치 | 내용 |
|---|---|---|
| `epa/epanet_gunsan/epanet_si_gs.py` | `:930-934` | 임계값 `98.0` → `95.0`, 오류 문구와 `note` 의 "98" → "95" |
| `epa/epanet_gunsan/epanet_mo_gs.py` | `:774-778`, 모듈 docstring `:29` | 동일 |
| `epa/epanet_gunsan/main_epa_gs.py` | `:1192-1196` | 동일 (PRE 예측 엔진) |

```python
elif vid == "지방산단밸브":
    if opening < 95.0:
        raise ValueError(f"지방산단 개도율 {opening:.5f}%: 후단 압력과 부분 개방 곡선이 없어 95% 미만을 적용할 수 없습니다.")
    status = "OPEN"
    old.initial_status = wntr.network.LinkStatus.Open
    note = "95~100% 전개방 근사; 후단 압력 및 부분 개방 보정곡선 없음"
```

`main_epa_gs.py`(PRE 예측 엔진)는 별도 컨테이너 `ems-epa-pre`
(`deploy/gunsan/docker-compose.prod.yml`)에서 돌아 웹 버튼 경로와 무관하지만, **같은 실측
태그를 쓰므로 95%대 개도율에서는 똑같이 실패한다.** 세 엔진이 어긋나면 "SI 는 되는데 PRE 만
죽는" 상태가 되므로 함께 맞췄다.

**검증은 SI 로만 했다(§8.2).** MO·PRE 는 코드가 글자 단위로 같고(§2.3) 구문 검사만 통과시켰다.

### 8.2 검증 — 해석이 끝까지 돌았다

더미는 그대로 두고(`891-365-POI-8600 = 95.36875`, 실측값) SI 엔진을 다시 실행했다.

지방산단밸브 해석 유량 `500.0 m3/h` 가 나운(배) 입력 수요 `500` 과 일치한다 — 이 밸브를

### 8.3 남는 한계 — 임계값을 낮춘다고 정확해지지는 않는다

`95~100%` 구간은 여전히 **저항 0 의 전개방으로 근사**한다. 임계값을 낮춘 것은
"더 넓은 범위를 같은 근사로 받아들이기로 했다"는 뜻이지, 95% 개도의 손실을 계산하게 된 것이
아니다. 근사 오차는 오히려 커진다.

제대로 풀려면 둘 중 하나가 필요하다.

1. **지방산단밸브 보정곡선 적합** — 국가산단처럼 개도율→저항 곡선을 만든다.
   `fit_gunsan_valve.py` 가 국가산단에 쓴 방식 그대로다.
2. **후단 압력계 확보** — `VALVE_META["지방산단밸브"]["downstream_pressure"]` 가
   `None` 인 것이 근본 제약이다(`:91`). 전·후단 차압이 있으면 `measured` 모드처럼
   실측에서 저항을 직접 계산할 수 있다.

### 8.4 벤더 드롭 시 재적용 필요

`epa/epanet_gunsan/*.py` 는 벤더가 파일 단위로 통째로 새로 준다. **드롭을 받으면 이 변경이
조용히 98 로 되돌아간다.** 받을 때마다 §8.1 을 다시 적용할 것.
